4. Baseline before the first edit: build for the iPhone 17 Pro simulator (use the `DEVELOPER_DIR` override from the xcode-build-and-sim-workflow memory), take light and dark screenshots of the phase's screens, and add the `#if DEBUG` publish counter from section 1 if it does not exist yet. Keep the screenshots for the end-of-phase diff.
5. Work the steps in order. After each step: build, run the relevant `-launchTab` / debug arg, screenshot, compare. Tick the step's box in this file when it is done and verified, not when it is written.
6. Standing rules that apply to every phase: no `git commit` or `git push` unless Abu asks in that message; no em dashes anywhere; the Equatable rule from the equatable-render-signatures memory (a row's `==` must fold every Settings field its body reads, and an `@ObservedObject` inside an Equatable view bypasses `==`); pre-iOS-26 chrome rules from memory; do not change the launch finale timing or curves (`LaunchScreen.swift` 900 ms hold + 500 ms fade); do not touch the prayer astronomy; watch never receives reading themes.
7. Anything under "Decisions pending Abu" is not to be done unless Abu answers. Ask at the start of the session if the phase touches one, then keep going with everything else.
8. End of session: append a progress-log entry (date, phase, steps done, files touched, what was verified and how, what is left), update the status table, remind Abu the changes are uncommitted, and update the performance-optimization-plan memory pointer if the file moved or the phase order changed.

## 0. Decision record: performance before bugs

Abu asked whether to fix bugs/crashes/glitches first or performance first. The answer given (and Abu's plan): **performance first, with a one-day crash triage in front of it.** Reasons, kept here so a later session does not re-litigate:

1. **The complaints are about lag, and the lag has one dominant cause.** One `Settings` object (26 `@Published` + 210 `@AppStorage` fields) is observed by 324 views across all five tabs, and all five tabs stay mounted after launch. Every write to any field re-evaluates everything. Fixing that touches the same files that most "glitch" reports come from (animated list relayout during a GPS fix, double re-renders after a toggle, countdown flicker). A good share of the visible glitches will disappear as a side effect, so fixing bugs first means fixing some of them twice.
2. **Performance work here is structural.** Splitting Settings, making navigation links lazy, gating materials, and moving loaders off-main change the shape of many views. Bug fixes written before that would land on code that is about to be reshaped.
3. **Crashes are the exception.** A crash is worse than lag. Before Phase 1, Abu spends a day in Xcode Organizer (Crashes, Hangs, Launch Time, Disk Writes) and any crash with a real count gets fixed first. The Hangs report also shows which of the main-thread stalls below actually fire on users' devices, which is the best prioritisation signal available. If Abu shares Organizer numbers, put them in section 1.

Order: crash triage (1 day, Abu) → Phase 1 Settings → Phase 2 extensions → Phase 3 launch → Phase 4 Adhan → Phase 5 Quran → Phase 6 Islam → Phase 7 Hadith → then the bug/glitch backlog, re-triaged against what is still reproducible.

## 3. Phase 1: Settings (and the foundation every later phase uses)

**Goal.** One publish per user action, delivered only to views that read the changed field. Plus four cross-cutting helpers that Phases 2-7 will use.

**Why it lags today.**
- `Settings` (`Settings.swift:32`) has 236 publishing fields. `@AppStorage` inside an `ObservableObject` publishes `objectWillChange` on every write (the code relies on this at `Settings.swift:1380-1381`). 325 views observe the whole object, plus 4 raw `objectWillChange` sinks (`ForegroundAdhanPlayer.swift:48`, `QuranView.swift:2908`, `QuranPlannerView.swift:382`, `SurahView.swift:2502`), plus `WatchConnectivity.swift:157-161`.
- The root `App` body reads `accentColor`, `colorScheme`, `firstLaunch` (`Al-IslamApp.swift:44,64-66`) and `MainTabView` observes Settings (`:152`), so any publish re-evaluates the window, the tab bar, and all five tab roots (`AdhanView.swift:5`, `QuranView.swift:181`, `HadithView.swift:55`, `IslamView.swift:4`, `SettingsView.swift:55`).
- ~60 `didSet`s call `fetchPrayerTimes` synchronously (`Settings.swift:796-1041, 1143-1152`; offsets `926-1010`; angles `1085-1099`). Each call (`SettingsAdhan.swift:1644-1749`) runs the network monitor check, `updateDates` (a JSON decode), traveling check, solar math, a `Prayers` JSON encode + app-group write (`Settings.swift:547-555`), and a geocode Task. The offset Steppers auto-repeat on long press (`SettingsAdhanView.swift:498, 645-650, 1688, 1699`), so each tick is a full recompute and two or more publishes to 325 observers.
- Per-row modifiers subscribe to Settings: `ThemedListRowBackground` (`ViewExtensions.swift:689-690`) at 176 sites inside `ForEach`, `ConditionalListStyle` (`567-568`), `ConditionalGlassEffect` (`GlassEffect.swift:4`) at 205 sites, `AccentGlowOverlay`/`AccentWashedBackground` (`336, 473`, 90 screens). A 114-row list registers 114 extra subscribers per publish.
- Byte-hashing in render paths: `profileStatsStamp` (`Settings.swift:1433-1447`) hashes 11 `Data` blobs (up to 5 years of tracker marks, ~6,236 khatm keys) on every `ProfileSettingsRow` render (`ProfileView.swift:261-262, 281`) and on every publish via `AchievementWatcher.signature` (`Achievements.swift:1086-1100`).
- Unmemoized JSON accessors read from bodies: `hijriDate` decodes a string per read (`Settings.swift:725-732`; read per countdown tick at `PrayerCountdown.swift:270-275`), `specialEvents` rebuilds 12 tuples with Hijri calendar math per read (`767-790`), plus `favoriteEnglishTranslationIDs` (`1212`), `savedSajdahAyahIDs` (`1227`), `savedBrokenLetterAyahIDs` (`1239`), surah counts (`1428-1429`), `lastListenedAyah/Surah` (`SettingsQuran.swift:480-540`).
- Duplicate publishes: manual `willSet { objectWillChange.send() }` on top of AppStorage's own at `Settings.swift:1130, 1142, 1147, 1151`; `betaQiraatEnabled.didSet` sends again (`1519`); `1234, 1246`; `prayers?.setNotification = true` at the end of every scheduling pass (`SettingsAdhan.swift:2287`) republishes `prayersData`, so every toggle renders the Adhan tab twice.

## 11. Low Power Mode and old devices

After Phase 1 step 1, `PerformanceProfile.tier` is `.reduced` when Low Power Mode is on, the thermal state is serious/critical, Reduce Motion or Reduce Transparency is on, or the device has < 4 GB RAM or ≤ 6 cores. Under `.reduced`:

- Materials → flat fills (`GlassEffect.swift`), shadows → none (`.softShadow`), `AccentGlowOverlay` → clear.
- Sky tick 300 s, starfield paused, compass off in the row, no GPS burst, countdown 60 s tier only.
- No prewarm sweeps beyond last-read ± 2, no lexicon, no embeddings, no corpus builds, no per-book hadith corpora, hadith `textBudget` ≥ 2 blocks.
- Launch: no page-mode settle beyond readiness, no finale blurs.
- Watch-sync debounce 2 s, location cadence 15 min, khatm auto-mark 1 s, widget reloads for prayer-time changes only.
- `NowPlayingView` 1 s, achievements burst/shine off, Islam pop springs and ring rotation off, `MasjidView` fan-out 2.
- Idle timer never disabled.
- Liquid Glass off (2026-09-04, Abu's interjection): `AppearanceEnvironment.liquidGlass` is false under Low Power Mode when `classicLookInLowPower` is on (default), and always when the Appearance toggle `classicLook` is on. `ConditionalGlassEffect` then takes its pre-26 fallback on all ~207 sites (flat fills on the reduced tier), `adaptiveSafeArea` becomes a plain inset, the search field gets its opaque backing, the Islam quote card drops its glass-only layer. The system's own tab bar, navigation bars, toolbars and sheets stay Liquid Glass; only the build-time `UIDesignRequiresCompatibility` key changes those, and it is app-wide.
- All `.utility` loaders (article corpus, WordByWord) either deferred or raised to `.userInitiated` once the user has actually requested the feature, because `.utility` is the tier Low Power Mode throttles hardest and a half-finished inflate collides with the first tap.

Today the gate exists (`AppPerformance`, 10 real consumers) but is static, so a view already on screen keeps whatever it decided at its last body evaluation. Making it observable is the whole point of Phase 1 step 1.
