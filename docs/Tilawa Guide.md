# Al-Islam Tilawa Port Guide

Working document for Claude Code sessions. Not user-facing. Abu asked for this on 2026-09-07, at the end of the day that ported Tilawa's features (Jamil Hammoudeh's app, borrowed with his permission) in three rounds plus the unmark-confirmation round, so that later sessions can take the ported features one by one and bring each up to the rest of the app: efficient, correct, finished, and measured. Nothing in the code was changed when this was written; it is a read-only audit of the 2026-09-07 tree (every Tilawa file read end to end, 13,686 lines across 22 files, plus every call site, the four rounds' diffs, the builders, and the Tilawa source for what was not ported).

The Performance Guide (docs/Performance Guide.md) is the parent document. Its foundation is assumed here and not re-explained: `PerformanceProfile` and the reduced tier, `AppearanceEnvironment` instead of observing `Settings`, the Equatable render-signature rule, `LiveState`/`ReadingState`, the one-sheet-host-per-list rule, `LazyDestination` for every pushed screen, off-main decoding with a spinner, `-renderCounter`/`-publishCounter`/`-publishTrace`, the post-reveal schedule in `Al-IslamApp`, and the `HADITH BLOCK ... MAIN|bg` decode log. The port was written fast, in one day, on top of that foundation but not always with it: the phases below are mostly the foundation applied to the new code, plus the product gaps the audit found.

## How to run a phase session

1. Read sections 0 to 2, the phase section Abu named, sections 13 to 17, and the appendix. Skim the other phases for cross-references ("Phase 4 step 6" etc.).
2. Every `file:line` here is from the 2026-09-07 tree after the unmark round (uncommitted at the time of writing, on top of commit c0a9b96 "Version 4.6.4 - Save 4", which carries rounds 1 and 2). Re-grep the symbol before editing; never trust the number.
3. Standing rules, all of them, every phase: no `git commit`/`push`/history rewrite unless Abu asks in that message; no em dash anywhere and no spaced hyphen standing in for one in user-facing text (`dashes.py` from the no-dash memory sweeps a build); never edit Quran or hadith text; the Hadith Encyclopedia's narrations (title, intro, body) render exactly as published (licence) and every encyclopedia screen keeps its credit; the Miracles articles keep their credit footer and their third-party quotes stay short and attributed; always the iPhone 17 Pro simulator (Abu tests iOS 18.6 on the iPhone 15 Pro simulator for pre-26 chrome); never edit sources while a build runs; the Equatable rule from the equatable-render-signatures memory; pre-iOS-26 chrome rules; the watch never receives reading themes.
4. Target membership, because it bit three times on port day: Quran, Islam and Settings files compile for the Watch too (`#if os(iOS)` around UIKit, `ThemeTopic`, the explorer, anything AppKit-shaped); Hadith files are iPhone-only; `DailyRollover.swift` and `ActivityLog.swift` compile for EVERY target (iPhone, Watch, Widget, Complication), so they may reference `Settings` but nothing else; `QuranOpenTarget` and `AppNavigation` sit outside `#if os(iOS)` in SunnahReminders.swift because QuranView's signatures reference them in the Watch build. A new resource pack must be REGISTERED (`Scripts/xcode_register.py <pack> --like <a sibling pack in the SAME folder>`) or `isBundled` is silently false; `--like` a file in another folder puts the entry in the sibling's group with a wrong path.
5. Baseline before the first edit: build Debug for the iPhone 17 Pro (the `DEVELOPER_DIR` override from the xcode-build-and-sim-workflow memory), run the phase's launch args from section 17, take light and dark screenshots, and record the counter readings the phase's Verify block asks for. Keep the screenshots for the end-of-phase diff.
6. Work the steps in order. After each step: build, run the relevant args, screenshot, compare. Tick the step's box in this file when it is done and verified, not when it is written.
7. Builders: a content change on Tilawa's side is a rebuild here (`Scripts/build_*.py [/path/to/Tilawa]`, default `~/Downloads/Islam/Tilawa`), then `Scripts/verify_*.py` where one exists, then a Debug build and a screenshot of the surface. Never hand-edit a pack.
8. Anything under "Decisions pending Abu" is not to be done unless Abu answers. Ask at the start of the session if the phase touches one, then keep going with everything else.
9. End of session: append a progress-log entry (date, phase, steps done, files touched, what was verified and how, what is left), update the status table, remind Abu the changes are uncommitted, and update the tilawa-port-2026-09-07 memory if a rule or a file moved.

## Decisions made

Kept here so a later session does not re-litigate them. All 2026-09-07 unless noted.

- Abu, 2026-09-08 ("ABCDE whatever u want whatever u think is best. Maximize efficiency performance optimization speed"), so A to E were taken this session with speed as the tiebreaker:
  - **A. The Hadith Encyclopedia is an on-demand container** (`Resources/Data/Hadith/HadeethEnc.henc`, option 3): a 143 KB xz header (the topic tree and one light row per narration) plus nineteen xz blocks of 128 full narrations. The door parses the header alone (684 KB, 15 ms) instead of 14 MB of JSON (217 ms), a narration inflates its own block (715 KB, 5 ms), and the search folds are built as bytes on the first search of a language (342 ms, was 1,594 ms). The reader's blocks ride in a three-entry cache; `unload()` and the memory-warning trim hand everything back.

The hadith typo vocabulary ships** (`Resources/Data/Hadith/HadithVocabulary.txt.xz`, 77 KB): the app exports its own walk (`-exportHadithVocabulary`), `Scripts/build_hadith_vocabulary.py` packs it behind a shelf fingerprint, and the runtime walk of all seventeen books stays only as the fallback when the list is missing or was built for other packs.
  - **C. The watch mirrors its activity days.** The watch sends its last thirty active days in the settings payload (`Settings.watchActivityKey`, watch to phone only); the phone merges them into `ActivityLog.watchDays`, which every count, total and streak folds in. The analytics footer says so now.
  - **D. The dua slots are seeded.** The jitter and the pick come from a SplitMix64 generator seeded by the slot's own calendar day, index and slots-per-day, so every pass on a given day rebuilds the same times and the same duas.
  - **E. What to port next: the audio extras first** (sleep timer, playback speed, reciter preview, curated collections: one session, all local), then Hifz mode as the next large rock, with the Sunnah fasting markers (white days, Monday and Thursday, the Tashriq carve-out) as a cheap win alongside. Not started; Phase 10 keeps the sizing.

## 1. Measure first

Take a baseline at the start of the first phase session and again at the end of every phase; record it in the progress log.

**What the simulator can and cannot tell.** The iPhone 17 Pro simulator is fine for body counts, publish counts, thread names in the decode log, memory footprint deltas and screenshots; useless for timing (an M-series Mac inflates LZMA at roughly 130 ms per 2 MB block; A12 is slower; launch marks swing 400 ms run to run). When a Verify block needs a real device, say so in the closing report instead of claiming it passed.

**Tools that already exist (all DEBUG, all in Globals.swift unless noted).**
- `-renderCounter`: `RenderCounter.hit("Label")` at the top of a body prints "RENDER COUNT" once a second; `ObjectPublishCounter.attach(object, label:)` prints "OBJECT PUBLISH"; `MemoryFootprint.log("label")` / `logLater` prints "FOOTPRINT label MB". The port's views carry NO `RenderCounter.hit` calls (grep: zero across the 22 files), so Phase 8 step 3 adds them and every phase's counts depend on that.
- `-publishCounter` ("PUBLISH COUNT n /s" for Settings, "WIDGET RELOAD n kinds") and `-publishTrace` (the caller of every Settings publish, demangle with `swift demangle`).
- `-launchTiming` prints the launch timeline; `HADITH BLOCK <kind> <slug>#<block> <ms> MAIN|bg` under `-renderCounter` names every hadith decode and its thread; `PACK PARSE <name> <KB> <ms> MAIN|bg` (Phase 1) does the same for the daily corpora; `SNAPSHOT quran|daily <bytes>` under `-publishCounter` prints every widget blob save; `-dailyWidgetsForce` rewrites the daily blob on that launch; `-dailyRolloverProbe` logs `DAILY ROLLOVER ... agree=1` (Phase 1 step 11).
- `-lowPowerMode`, `-perfTierReduced` for the reduced tier on the simulator.
- `-auditPacks` fingerprints the bundled packs (PackAudit.swift), but its loose-payload list (:184) does not yet name any Tilawa pack: Phase 9 step 3.

**Recipes.** The scratchpad is per session, so the two scripts every phase needs are written out here rather than referenced.

Log capture (the `islamlog.sh` pattern): start `xcrun simctl spawn <UDID> log stream --predicate 'processImagePath CONTAINS "iPhone"' --style compact > out.log &`, then `xcrun simctl launch <UDID> com.Quran.Elmallah.Islamic-Pillars -renderCounter <args...>`, wait N seconds, `kill %1`, then grep the log for `RENDER COUNT`, `OBJECT PUBLISH`, `HADITH BLOCK`, `PACK PARSE` (Phase 8 step 4 adds it), `FOOTPRINT`. Screenshots with `xcrun simctl io <UDID> screenshot`. Taps with idb (`~/Library/Python/3.9/bin/idb ui tap x y --udid <UDID>`; the first tap after a swipe is swallowed by scroll settling; swipes from y=700 hit the picker, start at y=600).

Idle count (the `regress.sh` pattern): launch with `-renderCounter -launchTab<X>`, wait 8 s past the reveal, then count `RENDER COUNT` lines whose totals change over the next 10 s. Target: zero body evaluations per second on every tab while idle, which the 2026-09-05 pass measured and which the port must not have broken (the Islam root now hosts `ReminderOfTheDayCard` with four observers, the Quran root the Word of the Day tile, the Hadith root the topics door).

**Numbers to take per phase.** Main-thread pack parses at launch (grep `PACK PARSE ... MAIN` once it exists; today read the code paths in section 2); body evaluations of the phase's root-mounted views per Settings publish; publishes of the phase's stores per user action; `FOOTPRINT` before and after the phase's heaviest screen; the widget snapshot's byte count (print `data.count` in `QuranWidgetStore.save` under `-publishCounter`); the first-query latency of each search lane (add a `RANKED <lane> <ms>` NSLog under `-renderCounter`, Phase 4 step 1).

**Definition of done for the port.**
- No pack parse and no JSON decode on the main thread from a view body anywhere in the ported code (the Performance Guide's rule 7, restated).
- Zero idle body evaluations on every tab with the port's root cards mounted.
- Every ported screen root and root-mounted card carries a render label and reads accent and faces from `AppearanceEnvironment`, never `@ObservedObject settings`, unless it is Equatable and folds what it reads.
- The widget snapshot the four Quran widgets decode is no bigger than before the port; the daily corpus lives in its own blob.
- Every store that holds more than a megabyte (encyclopedia, Miracles library and image cache) answers the shared memory-warning hook.
- Every pack has a builder, a verifier or a build-time check, a registration, an `-auditPacks` row, and a credit.
