## 1. Read this before you touch anything

### The extraction PDFs are NOT the ones in `Resources/Mushaf PDFs/`

This is the single most expensive trap in this workflow and it cost most of a session.

| | `Resources/Mushaf PDFs/*.pdf.xz` | archive.org originals |
|---|---|---|
| ships in the app | yes | no |
| page count, glyphs | correct | correct |
| segments to 6236 | yes | yes |
| **inter-word spaces** | **~12,000 destroyed per volume** | intact |
| khalaf ayahs matching | 5,035 / 6,236 | reference |
| Shubah round-trip | **71.87%** | **89.09%** |

The shipped copies were unflated and re-xz'd to save space. That merged text spans, so
words run together. A page still *looks* perfect and still segments correctly, which is
exactly why this is dangerous - the corruption is invisible until you diff the text.

Measured by building the caches from each source in turn and round-tripping (see the cache
warning below: the two runs must not share a cache, or the second silently reuses the first).

`extract.pdf_path()` now **refuses** the shipped copies and prints the download URL.
Override only for a structural check, never for text you keep:

```bash
QIRAAT_ALLOW_SHIPPED_PDFS=1 python3 extract.py segment khalaf   # degraded, warns loudly
```

The real extraction PDFs are saved at:

```
/Users/theabubakrabu/Downloads/Islam/qiraat-extraction-pdfs/     (84 MB, 10 volumes)
```

Symlink or copy them into `_staging-riwayat/pdfs/` before running anything:

```bash
cd Resources/JSONs-Deprecated/Qiraat/_staging-riwayat
ln -sf /Users/theabubakrabu/Downloads/Islam/qiraat-extraction-pdfs/*.pdf pdfs/
```

If that folder is ever lost, re-download from
<https://archive.org/details/quran-islamweb.net> using the filenames in `pdfs/README.md`.
Everything else the pipeline needs **is** in the repo.

### `raw_ayahs` caches the PDF parse and NEVER checks whether the PDF changed

`extract.raw_ayahs()` writes `data/<slug>.raw.json` (~17 MB per volume) and, if that file
exists, returns it without opening the PDF at all. So after you point the pipeline at a
different source, **every later run silently reuses the old parse**. This burned an hour:
the PDF path and md5 printed correctly while the output stayed degraded, because nothing
was reading the PDF.

**Whenever you change PDF source, delete the caches first:**

```bash
cd Resources/JSONs-Deprecated/Qiraat/_staging-riwayat/pipeline
find data \( -name "*.raw.json" -o -name "*.surahs.json" \) -delete
```

Both are now gitignored, along with `pdfcache/` and `emit/`. Regenerating costs ~1 min per
volume, which is far cheaper than trusting a stale one.

### Two volumes cannot be used as bridges

`01-asim-hafs.pdf` and `03-ibn-kathir-al-bazzi.pdf` encode ayah numbers differently:
Hafs yields **0 ayah markers** where Shubah yields exactly 6,236, and Bazzi finds 6,220
markers but will not split into 114 surahs. The `pipeline/data/README` note calling Hafs
"the strongest untapped bridge" is therefore not actionable without writing a new marker
detector for that volume. **Shubah remains the only Kufi bridge.**

## 2. What the pipeline actually is

The `learn` phase (EM over glyph→Unicode) is **not** on the critical path and takes ~35 min
for nothing. The path that produces text is:

```
segment  →  detmap  →  ctxpass  →  roundtrip  →  emit
```

```bash
cd Resources/JSONs-Deprecated/Qiraat/_staging-riwayat/pipeline

python3 extract.py segment shubah khalaf khallad   # PDF → data/<slug>.surahs.json
python3 final.py   detmap                          # glyphcounts → detmap-<family>.json
python3 final.py   ctxpass kufi shubah             # neighbour-conditioned rules
python3 final.py   roundtrip shubah                # THE acceptance metric
python3 final.py   emit khalaf khallad             # → pipeline/emit/ (safe by default)
```

`emit` now writes to `pipeline/emit/` instead of straight into `Resources/Data/Quran`.
To actually ship, review the diff first, then:

```bash
QIRAAT_EMIT_DIR=../../../../Data/Quran python3 final.py emit khalaf khallad
```

Needs `pymupdf` and `fonttools` (`python3 -m venv venv && venv/bin/pip install pymupdf fonttools`).

Verified 2026-08-24 from a clean repo checkout with caches cleared: `roundtrip shubah`
gives **89.46%**, and `emit khalaf khallad` reproduces `*.v2-candidate.json`. If you do not
get 89.46%, you have a stale cache.

Two extra steps belong in the chain after `segment`, before `emit`:

```bash
python3 fixdrops.py khalaf khallad   # resolve/park glyphs emit would silently discard
python3 zoneaudit.py                 # re-check nothing is mapped across the baseline
```

`data/ctxrules.json` and `data/glyphfuzzy.json` are `learn` artefacts that were missing from
the committed snapshot; they are restored now. Neither affects segmentation (verified: the
same 78,861 space tokens with and without `ctxrules.json`), but keep them.

### Acceptance metric

`final.py roundtrip shubah` renders the Shubah volume and diffs it against the app's
KFGQPC-verified Shubah text. **Never accept a change that lowers it.**

|---|---|
| as committed before this session | 87.29% |

## 3. What changed in this session

### New tools (`pipeline/`)

| file | what it does |
|---|---|
| `zoneaudit.py` | **The key idea.** Kasra/kasratain are drawn *below* the baseline; fatha, damma, shadda, sukoon, maddah, dagger-alef *above*. Any glyph whose ink sits on the wrong side of the baseline for the mark it emits is provably mismapped. Finds **21 violations**. |
| `glyphsheet.py` | Renders glyph outlines to a labelled PNG contact sheet so you can *look* at a glyph instead of guessing. `GLYPH_VOLUME=khallad python3 glyphsheet.py '[["Hamd2",170,"note"]]' /tmp/g.png` |
| `fixmarks.py` | Applies the verified mark corrections into `manualmap.json`. |
| `hamd_imalah.py` | Maps the Khallad volume's Hamd2 imalah dots (see below). |
| `dumpword.py` | `python3 dumpword.py shubah 2 69 "سُر"` - dumps one word's glyph keys with their emissions. Best first move on any single-word bug. |
| `showdrops.py` | `python3 showdrops.py khalaf khallad` - every word `emit` is silently losing a glyph from, beside the Hafs word. Run this before believing an "unresolved" count: most of it is page furniture. |
| `fixdrops.py` | Sorts those into REAL (mapped) vs FURNITURE (parked in `droplist.json`) and prints anything it cannot classify. |
| `findglyph.py` | `python3 findglyph.py khalaf HQPB1#149` - every word containing a given font#gid, with the Hafs word beside it. |
| `findpage.py` | `python3 findpage.py khallad 2 62 /tmp/p.png 0.05 0.45` - renders the PRINTED page holding an ayah. **The tiebreaker.** Settled both the imalah question and Ishaq/Idris in one look each. |
| `blame.py` | Ranks glyph keys by attributed character errors. Partially defeated by the post-passes; `dumpword.py` is usually better. |

Fonts are resolved **by name**, never by hardcoded xref - the shipped `.pdf.xz` copies
renumber xrefs, which silently breaks anything that hardcodes them.

### Source changes

- `extract.py` - `APP` repointed to this repo; `pdf_path()` hardened (above); Hafs added to
  `BRIDGES` via a `__quran__` special case in `overlay()` (harmless, but see §1, unusable);
  **`_is_imalah_dot()` added** and wired into `page_tokens`, so the imalah dot is recognised
  in both of its spellings (`HQPB5#20` and `MSH-Quraan1#38`) and routed through the existing
  geometric dot-attachment. `MSH_IMALAH_GID = 38` is no longer dropped with the MSH layer.
- `final.py` - `APP` repointed; `emit` destination defaults to `pipeline/emit/`;
  **`ctxpass` now force-targets zone-violating keys**. This mattered: those glyphs have
  >90% *wrong* purity, so they were never targets, which meant `ctxpass` **pinned** them to
  the wrong emission and was structurally forbidden from ever correcting them.
- `final.py` - **`collapse_doubled_marks` now folds a repeated mark SEQUENCE**, not just a
  repeated character. A glyph carrying two marks (`HQPB4#38` = kasra + small low meem)
  double-draws as `ِِۭۭ`, where no two adjacent characters are equal, so the old rule saw
  nothing to remove and the doubling reached the shipped text.
- `decode.py`, `hybrid.py`, `validate.py`, `ishaq_keys.py` - `APP` path only.

## 4. Imalah: RESOLVED, and it went through two wrong answers first

Both volumes mark Hamzah's imalah in full. Getting there needed three corrections, and the
wrong turns are worth knowing because the same trap will recur on the other riwayat.

1. Khallad emitted 152 marks against Khalaf's 1,348, so it looked like a volume that does
   not mark imalah. **Wrong.** Khallad draws the dot in the `Hamd2` font (gids
   166/170/171/172, a filled dot below the baseline); the pipeline had no Hamd2 mapping and
   discarded ~1,737 of them. `hamd_imalah.py` recovers those.
2. That left Khallad at 1,878 and Khalaf at 1,348, i.e. 523 words Khallad marked and Khalaf
   did not, which looked like Khallad over-marking. **Also wrong.** Every one of the 523 is
   a textbook imalah word (`ٱلنَّصَٰرىٰ`, `بُشۡرىٰ`, `أُنثىٰ`, `ٱلدُّنۡيا`, `جآءَ`), so it was
   *Khalaf* that was short.
3. Rendering the printed page settled it: **both** volumes ink a red dot under
   `ٱلنَّصَٰرىٰ`. Khalaf draws it in `MSH-Quraan1` gid 38, and `page_tokens` was dropping
   that whole layer as page furniture (`MSH` is in `DROP_PREFIX`). 2,846 dots in Khalaf
   against 24 in Khallad, all discarded.

`extract._is_imalah_dot()` now recognises both spellings (`HQPB5#20` and `MSH-Quraan1#38`)
and routes them through the existing geometric dot-attachment, which normalises them to one
token, so `render_det` needed no change.

| | shipped | now |
|---|---|---|
| khalaf imalah | 1,343 | **1,884** |
| khallad imalah | 152 | **1,884** |
| agreement on identical words | 123 | **1,850** (9 khalaf-only, 10 khallad-only) |

Two rawis of one qari agreeing on 1,850 of ~1,884 imalah positions is the expected result:
imalah is Hamzah's usul, shared by both. **The earlier caveat about 523 suspect marks is
withdrawn.**

**The general lesson:** before concluding a mark is absent from a volume, check whether that
volume draws it in a different font, and check whether that font is being dropped as
furniture. Two separate fonts (`Hamd2`, `MSH-Quraan1`) hid the same mark in this one pass.

## 5. The idgham-shadda asymmetry is genuine

khalaf carries ~3,400 idgham shaddas (a shadda on the following word's first letter after
tanween/noon-sakin, e.g. `غِشَٰوَةٞۖ وَّلَهُمۡ`) and khallad carries none. Fresh extraction of both
volumes with identical machinery reproduces it (khalaf 26,249 shaddas, khallad 22,632), so
it is a **property of the two printed volumes**, not an extraction artefact.

Unlike the imalah case this one held up, because it is not about a missing glyph mapping.
**Do not normalise it in either direction** without a qari's ruling. Note the app's other
19 riwayat follow the KFGQPC convention (no such shadda), so khalaf will look different in
comparison mode. That is faithful to its source.

Dropped glyphs are **done**. `emit` now discards 2 occurrences in khalaf and **0** in
khallad, down from 418 and 2,106. What that hid:

* ~95% of the old count was page furniture (the decorative basmalah at each surah head,

* Real text recovered: the muqatta'at maddah (`ٱلٓم✗` → `الٓمٓ`), the sheen and qaf of

* `collapse_doubled_marks` now folds a repeated mark *sequence*, not just a repeated
  character: a glyph carrying two marks double-draws as `ِِۭۭ`, which the old
  per-character rule could not see.

Still open:

1. **15 (khalaf) / 18 (khallad) scrambled words** remain: `جَبۡرَِيل` (should be `جَبۡرَئِيل`),

2. **14 zone-violating shadda glyphs** (`HQPB4` 65,67,68,69,70,73,74,75,76,77,79,80,81,82):
   the same shadda outline at climbing stack heights, all mapped to kasra. Do **not**
   blanket-override; measured bare shadda 55.55%, shadda+kasra 78.00%, left alone 88.91%.
   They are ctxpass targets now; they need better context evidence, not a flat mapping.
3. `PAUSE-EDITION` ×307 is an **edition difference** (different waqf system), not an error.
4. `RASM` ×125 is unexamined and is the next real class to attack.
5. Two stray singletons in khalaf (`HQPB5#129` at 10:3, `HQPB4#216` at 53:23).

### Ishaq / Idris are identical IN THE SOURCE, not because of a bug

Previously logged as a pipeline defect. It is not one. Both volumes were re-downloaded and
re-extracted from their own PDFs:

* the two PDFs are genuinely different files (md5 `b648f9b5…` vs `81dcf3b0…`, 8,137,508 vs
  8,198,511 bytes);
* their extracted glyph streams are **byte-identical** (700,987 tokens, same hash);
* rendering the same page from each shows identical Quranic text, differing only in the
  header: `برواية إسحاق عن خلف العاشر` vs `برواية إدريس عن خلف العاشر`.

**Islamweb published one body text under both rawi names.** Our identical
`QiraahIshaq`/`QiraahIdris` are therefore faithful to the source, and fabricating
differences would be wrong. Ishaq and Idris do differ as riwayat, so this needs a product
decision rather than a pipeline fix: either label the pair as sharing a base text pending a
differentiated source, or source one of them elsewhere. Do not "fix" it in the data.

Their segmentation also needs `bootstrap=True` (basmalah-based surah detection fails on
these two volumes: 2 blocks instead of 114). With bootstrap they give a clean 114 surahs /
6,236 ayahs, but still ~1,815 unresolved glyphs each, so their private glyph layer needs
the same treatment Hamzah just received before their text is trustworthy.

### The method that worked

1. **Baseline first.** `final.py roundtrip <bridge>` before touching anything. Never accept
   a change that lowers it. Every claim below was accepted or rejected on this number.
2. **`zoneaudit.py`** - geometry finds mismapped marks with no guessing (kasra below the
   baseline, shadda above; anything crossing that line is wrong).
3. **`showdrops.py`** - see what `emit` is actually losing. Do not trust the raw
   "unresolved" count: 95% of Hamzah's was decorative page furniture, and the handful of
   real losses underneath it was invisible until they were separated. `fixdrops.py` does
   the separating.
4. **`glyphsheet.py`** on any suspect glyph. Reading the outline beats reasoning about
   emission statistics, which are confidently wrong surprisingly often.
5. **`findpage.py`** when two sources disagree and you need a ruling. Rendering the printed
   page settled both open questions of this session in one look each.
6. **Cross-compare the two rawis**, then against Hafs and Shubah. Where the two rawis of one
   qari disagree, at least one is corrupt: highest-yield list. Where they agree but differ
   from Hafs, it is probably genuine farsh. Where one rawi has a mark and the other does
   not, check the *words* are the right linguistic environment before believing either.
7. Re-run the round-trip. Keep only what does not regress it.
