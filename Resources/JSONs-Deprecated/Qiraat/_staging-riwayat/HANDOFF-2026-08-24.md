## 1. Read this before you touch anything

### The extraction PDFs are NOT the ones in `Resources/Mushaf PDFs/`

This is the single most expensive trap in this workflow and it cost most of a session.

| | `Resources/Mushaf PDFs/*.pdf.xz` | archive.org originals |
|---|---|---|
| ships in the app | yes | no |
| page count, glyphs | correct | correct |
| segments to 6236 | yes | yes |
| **inter-word spaces** | **~12,000 destroyed per volume** | intact |
| khalaf ayahs matching | 5,035 / 6,236 | reference |
| Shubah round-trip | **71.87%** | **89.09%** |

(Both measured against the same pipeline on the same day, so the gap is the point, not the
absolute numbers. The current acceptance figure is 90.56%; see §2.)

The shipped copies were unflated and re-xz'd to save space. That merged text spans, so
words run together. A page still *looks* perfect and still segments correctly, which is
exactly why this is dangerous - the corruption is invisible until you diff the text.

Measured by building the caches from each source in turn and round-tripping (see the cache
warning below: the two runs must not share a cache, or the second silently reuses the first).

`extract.pdf_path()` now **refuses** the shipped copies and prints the download URL.
Override only for a structural check, never for text you keep:

```bash
QIRAAT_ALLOW_SHIPPED_PDFS=1 python3 extract.py segment khalaf   # degraded, warns loudly
```

The real extraction PDFs are saved at:

```
/Users/theabubakrabu/Downloads/Islam/qiraat-extraction-pdfs/     (84 MB, 10 volumes)
```

Symlink or copy them into `_staging-riwayat/pdfs/` before running anything:

```bash
cd Resources/JSONs-Deprecated/Qiraat/_staging-riwayat
ln -sf /Users/theabubakrabu/Downloads/Islam/qiraat-extraction-pdfs/*.pdf pdfs/
```

If that folder is ever lost, re-download from
<https://archive.org/details/quran-islamweb.net> using the filenames in `pdfs/README.md`.
Everything else the pipeline needs **is** in the repo.

### `raw_ayahs` caches the PDF parse and NEVER checks whether the PDF changed

`extract.raw_ayahs()` writes `data/<slug>.raw.json` (~17 MB per volume) and, if that file
exists, returns it without opening the PDF at all. So after you point the pipeline at a
different source, **every later run silently reuses the old parse**. This burned an hour:
the PDF path and md5 printed correctly while the output stayed degraded, because nothing
was reading the PDF.

**Whenever you change PDF source, delete the caches first:**

```bash
cd Resources/JSONs-Deprecated/Qiraat/_staging-riwayat/pipeline
find data \( -name "*.raw.json" -o -name "*.surahs.json" \) -delete
```

Both are now gitignored, along with `pdfcache/` and `emit/`. Regenerating costs ~1 min per
volume, which is far cheaper than trusting a stale one.

### Two volumes cannot be used as bridges

`01-asim-hafs.pdf` and `03-ibn-kathir-al-bazzi.pdf` encode ayah numbers differently:
Hafs yields **0 ayah markers** where Shubah yields exactly 6,236, and Bazzi finds 6,220
markers but will not split into 114 surahs. The `pipeline/data/README` note calling Hafs
"the strongest untapped bridge" is therefore not actionable without writing a new marker
detector for that volume. **Shubah remains the only Kufi bridge.**

## 2. What the pipeline actually is

The `learn` phase (EM over glyph→Unicode) is **not** on the critical path and takes ~35 min
for nothing. The path that produces text is:

```
segment  →  detmap  →  ctxpass  →  roundtrip  →  emit
```

```bash
cd Resources/JSONs-Deprecated/Qiraat/_staging-riwayat/pipeline

python3 extract.py segment shubah khalaf khallad   # PDF → data/<slug>.surahs.json
python3 final.py   detmap                          # glyphcounts → detmap-<family>.json
python3 final.py   ctxpass kufi shubah             # neighbour-conditioned rules
python3 final.py   roundtrip shubah                # THE acceptance metric
python3 final.py   emit khalaf khallad             # → pipeline/emit/ (safe by default)
```

`emit` now writes to `pipeline/emit/` instead of straight into `Resources/Data/Quran`.
To actually ship, review the diff first, then:

```bash
QIRAAT_EMIT_DIR=../../../../Data/Quran python3 final.py emit khalaf khallad
```

Needs `pymupdf` and `fonttools` (`python3 -m venv venv && venv/bin/pip install pymupdf fonttools`).

Verified 2026-08-24 from a clean repo checkout with caches cleared: `roundtrip shubah`
gives **90.56%**, and `emit khalaf khallad` reproduces `*.v2-candidate.json`. If you do not
get 90.56%, you have a stale cache. **Clearing `data/*.surahs.json` is not enough**: the PDF
parse is cached separately in `data/*.raw.json`, so a change to `extract.py` needs both gone
or the re-segment quietly reuses the old glyph stream. That cost a full wrong measurement.

Two extra steps belong in the chain after `segment`, before `emit`:

```bash
# zone-correct the CONTEXT map. Run it for EVERY family: it can only see the ctx map of
# the one it is given, it MERGES into zoneflip.json, and a single-family run used to
# overwrite the others' rungs. See §3j.
for f in kufi madani basri; do QIRAAT_FAMILY=$f python3 zonectx.py --write; done
QIRAAT_MSH_VOLUMES="shubah <a> <b>" python3 mshmap.py --with-pauses   # the MSH farsh layer
python3 fixdrops.py khalaf khallad   # resolve/park glyphs emit would silently discard
python3 zoneaudit.py                 # re-check nothing is mapped across the baseline
```

`zonectx.py` and `mshmap.py` write into `data/`, so they only need re-running when you move
to a new family or change the fonts in play. The committed `zoneflip.json` and the MSH
entries in `manualmap.json` are already correct for the Kufi volumes.

`data/ctxrules.json` and `data/glyphfuzzy.json` are `learn` artefacts that were missing from
the committed snapshot; they are restored now. Neither affects segmentation (verified: the
same 78,861 space tokens with and without `ctxrules.json`), but keep them.

## 3b. The shadda ladder: the roles were SWAPPED, not simply wrong

Fourteen `HQPB4` glyphs (65, 67, 68, 69, 70, 73, 74, 75, 76, 77, 79, 80, 81, 82) are one
identical bare-shadda outline drawn at fourteen stack heights, and every one of them emitted
a **kasra**. The previous session flagged them and stopped, because forcing them to shadda
measured 55.55% against 88.91% for leaving them alone. That measurement was right and the
conclusion drawn from it was wrong.

The reason: this print draws a doubled letter as

```
    مِّن  =  [HQPB4#176 kasra stroke, ink BELOW]  [HQPB4#75 shadda, ink ABOVE]
```

in that stream order, while Unicode writes the shadda first. Rather than reorder, the EM
learner **swapped the two emissions**: the kasra glyph learned to emit a shadda and the
shadda glyph learned to emit a kasra. That yields the correct string for the pair, and
nonsense for every ladder glyph that turns up without its partner, which is where
`جَبۡرَِيل`, `يَٰبُنَِّ` and `ثُلُثَِ` came from. Fixing one half only (what 55.55% measured)
leaves the other half swapped and destroys the pair.

Two things had to change together:

1. **Both halves emit what their ink is.** `zonectx.py` audits the CONTEXT map the way
   `zoneaudit.py` audits the detmap, and writes `data/zoneflip.json`: ink above the baseline
   emitting a below-mark becomes the bare shadda; ink below emitting a shadda reverts to its
   own majority zone-consistent emission. 24 keys, 15 ladder and 9 partners.
2. **`reorder_shadda` puts the pair back into Unicode order** (`[vowel][shadda]` becomes
   `[shadda][vowel]`).

An unpaired ladder glyph now yields a bare shadda, which is what it is.

**The lesson worth carrying:** `render_det` consults `ctxdet-*.json` BEFORE `detmap`, so a
glyph can be zone-correct in the detmap and still render as the wrong mark. `zoneaudit.py`
alone cannot see that. Run `zonectx.py` too.

## 3c. The MSH-Quraan1 layer is the FARSH TEXT, and it was being thrown away

Every page prints its own colour legend at the foot:

| colour | meaning |
|---|---|
| magenta | الكلمة المخالفة لحفص, the word that differs from Hafs |
| blue | الإدغام |
| red | الإمالة |
| cyan | السكت |
| orange | إشمام الصاد صوت الزاي |

The magenta layer is drawn in `MSH-Quraan1`, which `DROP_PREFIX` discarded wholesale. The
HQPB body layer leaves a **zero-width spacer** where each of its glyphs goes, so nothing
looked missing: the word simply came out as if the farsh letter had never been printed.

Dropping that layer therefore deleted precisely the letters that make a riwayah a riwayah:

| ayah | printed | was extracted as |
|---|---|---|
| 2:97, 2:98, 66:4 | `جَبۡرَءِيلَ` | `جَبۡرَِيلَ` (the ء gone) |
| 6:55 | `وَلِيَسۡتَبِينَ` | `وَلَِسۡتَبِينَ` (the ي gone) |
| 22:4 | `تَوَلَّاهُ` | `تَوَِّٜهُ` (the لا gone) |
| 28:78 | `ذُنُوبِهُمُ` | `ذُنُوبِهمُ` (Hamzah's pronoun damma) |
| 20:133 | `يَأۡتِهِم` | `َأۡتِهِم` |
| 12:110 | `فَنُۨجِي` | `فَنُجِي` |
| 73:20 | `ثُلُثَيِ` | `ثُلُثَِ` |

`MSH_TEXT_GIDS` in `extract.py` now keeps every **inked** non-furniture glyph in that layer
(blankness decided by outline bounds, not by eye: 13 of the 37 gids are pure spacers, and
155/156 are the surah-banner rosette). `mshmap.py` holds the gid-to-Unicode map, one line
per gid, each commented with the word that settles it. About 160 glyphs across the three
Kufi volumes.

Two traps inside this one:

- **The layer double-draws its letters** (stroke pass, then fill pass), so `ء` arrived twice.
  The old dedupe only fired on combining marks. It now fires on any repeated identical glyph
  key, which also fixed a triple-drawn alef in `وَمِيكَٰٓـِٔيلَ`.
- **The hamza is a combining hamza, not a standalone ء.** `MSH#46` sits well above the
  baseline and belongs ON the alef beside it, but the page stacks it after the alef's vowel.
  Emitting `ء` produced `لَّٱللَّءَذَقۡنَٰكَ`, because a bare `اَ` is what the الله rule keys on.
  It now emits U+0654 and `compose_hamza` folds `ا` + `ٔ` into `أ` across any intervening
  vowels. `MSH#210`, which sits on the baseline, really is the standalone `ء`.

**Expect this layer in every one of the remaining riwayat.** Run
`python3 mshmap.py --evidence` first; the gid numbering is per-font and may not carry over.

## 3d. Al-Kisai: the ishmam dot, and a second banner in a second font

The Hamzah machinery transferred to Abu al-Harith and ad-Duri al-Kisai unchanged - same
604 pages, same font set, both segmenting to 114 surahs / 6,236 ayahs with no bootstrap.
What did NOT transfer was the farsh layer's gid numbering, exactly as §3c warned. Four
inked MSH-Quraan1 gids appear in these volumes and in neither Hamzah volume:

| gid | x | what the printed page shows | emitted |
|---|---|---|---|
| 39 | 115 | a filled dot where the kasra belongs, on قِيلَ and its six companions | `U+0650` |
| 101 | 41 | a tall thin stroke: the alef of Al-Kisai's `إِذَا دَبَرَ` (74:33) | `ا` |
| 49 | 4 | an upright oval zero over the ha of `يَتَسَنَّهۡ` / `ٱقۡتَدِهۡ` | `U+06E0` |
| 8 | 4 | the قلى waqf sign over `ٱلۡأٓخِرَةِۗ` (3:148) | `U+06D7` |

### The ishmam dot was deleting a vowel outright

Gid 39 lands on exactly nine forms and nothing else: `قِيلَ` x34, `وَقِيلَ` x15, `سِيٓءَ`,
`وَسِيقَ`, `وَغِيضَ`, `وَحِيلَ`, `جِيٓءَ`, `سِيٓـَٔتۡ`, `وَجِيٓءَ`. That is the classical
seven-word ishmam set, the words these readers blend from kasra toward damma. The print
puts the dot **in place of** the kasra, so dropping the MSH layer left the letter with no
vowel at all, and the shipped `QiraahAbuHarith`, `QiraahDuriKisai` and `QiraahHisham` all
read a bare `قيلَ` - 53 unvocalised words per volume, in three riwayat.

The text now gets a plain `U+0650`, because ishmam is a manner of pronouncing a kasra and
not a different vowel, and because every other riwayah writes these words that way. The
fact that the print marked them is preserved separately, in `data/ishmam-kasr.json`
(`python3 ishmam.py abuharith durikisai`), keyed (surah, ayah, word index) to match what
`build_tajweed_v2.py`'s `flags_for()` already consumes for the orange `ishmam_sad` rule.
Adding an `ishmam_kasr` companion there is the natural home for it; nothing is lost
meanwhile.

Ibn Amir prints the same dot and Hamzah does not, which is why the gid is missing from the
Khalaf volumes. **Check gid 39 again when Hisham and Ibn Dhakwan come up.**

### A second decorative basmalah, and a size rule that separates it

`fixdrops.py` reported `HQPB3#72/73/74` at 112 occurrences each - one per surah. These
volumes draw the decorative basmalah in HQPB3 (4,460 / 7,353 / 10,411 units wide) where
Hamzah used `Hamd2#198/199/200`. Furniture, now parked in `droplist.json`.

Gid 101 needed a sharper cut, because 40 of its 41 occurrences are a stray alef left over
from the surah-name banner line (`ا سُورَةُ ٱلۡمُرۡسَلَاتِ`) and only one is text. Key-based
droplisting cannot separate them - same key. **Span size can**: the MSH layer draws the
banner at 20pt and body text at 12-14pt with nothing in between, and at 20pt it is only
ever the rosette (155/156) and that alef, in all three Kufi volumes. Hence
`extract.MSH_BANNER_SIZE`.

### Al-Duri's extra imalah is genuine, and it is a whole class

Abu al-Harith carries 1,598 imalah marks and ad-Duri 1,941. On words whose letters are
identical the two agree 1,573 times and disagree once, so the entire gap is 342 words
where **ad-Duri replaces a fatha with the imalah dot and Abu al-Harith does not**:
`ٱلنَّارِ` x53, `ٱلۡكَٰفِرِينَ` x47, `ٱلنَّهَارِ` x12, `ٱلدَّارِ`, `دِيَٰرِهِمۡ`,
`يُسَٰرِعُونَ`. 306 of the 342 have a kasrated raa after the mark; the rest are kasratain
spellings of the same words plus the ذوات الياء set (`هُدَايَ`, `وَمَحۡيَايَ`, `مَثۡوَايَ`).
That is ad-Duri an al-Kisai's documented ذوات الراء profile, not an extraction asymmetry -
the opposite of the Khalaf/Khallad imalah gap of §4, which WAS one. Note the convention:
where the dot is drawn the fatha is not, so `هَ` becomes `هٜ` (U+064E gives way to U+065C).

## 3e. Ibn Amir: 55 ayahs that were never there, and one dot doing two jobs

### The Shami pair was segmenting to 6281, not 6226

`segment` reports 6281 ayahs for hisham and 6282 for ibndhakwan against a true Dimashqi
count of 6226, and `shami_fix.py` expects to be handed **6222**. It is not a regression:
the pre-Hamzah `extract.py` at 2fd68d7 produces the same 6281, so it has been true for as
long as these volumes have been read from the archive.org originals.

The excess is exactly the number of **zero-glyph ayahs**: 59 in hisham, 60 in ibndhakwan,
and none in any other volume. They are doubled ayah markers with nothing between them.
`segment` now drops them, which lands the pair on 6222, and `shami_fix.py` then recovers
the 4 markers lost across page boundaries to reach 6226 with per-surah counts matching the
shipped data exactly (7, 285+1, 200, 176, 122, ...).

Left in, they shifted every later ayah id by one, so **any earlier comparison of these two
volumes against Hafs or against the app's own text was misaligned**.

### One dot, two jobs, and a rule instead of a word list

Ibn Amir draws the bayna-bayna dot at **gid 40**, not Al-Kisai's gid 39 (Hisham has zero
of gid 39; Ibn Dhakwan has both). The gid numbering itself is stable - the same gid has
the same outline in every volume - but each volume embeds its own SUBSET, so a gid that is
blank in one is inked in another. `MSH_TEXT_GIDS` is now the union, and `mshmap.py` must
be re-run per family regardless.

Unlike Al-Kisai's, this dot serves two different phenomena:

| | words | what the dot means | must emit |
|---|---|---|---|
| ishmam | `قِيلَ` x33, `وَقِيلَ` x15, `سِيٓءَ`, `وَسِيقَ`, `وَغِيضَ`, `وَحِيلَ`, `جِيٓءَ`, `سِيٓـَٔتۡ` | it stands IN the vowel slot, replacing the kasra | `U+0650` |
| tasheel | `ءَأَنتُمۡ`, `ءَأَنذَرۡتَهُم`, `ءَأَسۡلَمۡتُمۡ`, `ءَأَقۡرَرۡتُمۡ`, `ءَأَشۡفَقۡتُمۡ`, ... | it annotates a softened hamza already written in full | nothing |

Both share one cluster key, so `manualmap.json` cannot separate them. `final.ishmam_dot`
decides from the **base letter the dot caps**: ishmam only ever caps ق س غ ح ج. No word
list, and it covers Al-Kisai's gid 39 unchanged. `HQPB7#7` is the body layer's own copy of
the same dot and obeys the same rule.

Hisham prints 58 ishmam words and 25 tasheel; **Ibn Dhakwan prints 6 and 6**, which is the
genuine difference between the two rawis, not a gap. Al-Kisai prints 58 and 0.

### Two invisible glyphs were doing visible damage

* `HQPB7#3` is **blank** (no outline at all), drawn 204 times in hisham. Unmapped it
  rendered as a dropped-glyph marker mid-word AND hid the base letter from
  `final.ishmam_dot`, which is why `قِيلَ` stayed broken after the dot itself was mapped.
* `HQPB4#6` is **0.02pt wide in all 108 of its occurrences across three volumes**, so it
  prints nothing anywhere - yet the EM gave it a confident three-character emission,
  `\u0650\u06e6\u06da`, and since it is drawn twice that put a junk word `ِۦِۚۦۚ` after 21
  muqatta'at ayahs.

Both now live in `fixdrops.SPACER_GIDS`. **A zero-width or outline-less glyph is never
text, whatever the learner says about it** - and unlike the unresolved ones, a spacer
usually carries a plausible detmap entry, so it never appears in an "unresolved" count.
`fixdrops.py` forces them into the droplist for that reason.

### The rest of the Shami farsh layer

`MSH#44` is the small waw and `MSH#16` the small yeh of the pronoun silah, and the vowel
before decides which is drawn (`نُورَهُۥ` 61:8 against `وَنِصۡفِهِۦ` 73:20). `MSH#13` is the
`لا` no-stop sign, `U+06D9`. `MSH#72` is a long diagonal kashida stroke inside the magenta
redraw of `ٱلۡمُخۡلِصِينَ`, a connector rather than a letter. All four were read off the
rendered outline beside the printed page.

## 3f. Abu Jafar: an absolute font size, and 5,786 unvocalised meems per volume

### One constant, calibrated on the wrong family, deleted the ayah numbers

`MSH_BANNER_SIZE = 18.0` came out of the Kufi volumes, which set their body at 12-14pt and
their surah banner at 20pt, so "18pt or larger is furniture" separated the two cleanly. The
Madani and Basri volumes set their body at **16 to 18.5pt**. On every page that happened to
be typeset at 18pt the rule threw the entire MSH layer away.

That layer is not decoration in these volumes. **MSH-Quraan1 gids 19-28 are the digits 0-9**,
and they are where the ayah numbers live: the rosette is `HQPB2#167 <digit> HQPB2#168`, with
the tens digit often in HQPB2 and the units in MSH, or both in MSH. Ibn Wardan lost the
numbers of 24 ayahs to this, **nine of them consecutively at the head of Maryam**, and with
19:1 through 19:9 unnumbered `segment` could not see the surah boundary at all: al-Kahf and
Maryam came out as one 203-ayah block, 113 surahs instead of 114.

The threshold is relative now, `MSH_BANNER_RATIO = 1.10` against the page's own dominant
HQPB size. Measured across every volume, MSH text sits at 0.86-1.03 of the body size and the
banner at 1.14 (shubah), 1.29 and 1.43 (khalaf). **Nothing lands between 1.03 and 1.14**, so
the ratio reproduces the old Kufi behaviour exactly while unblocking the other two families.

After the fix both volumes segment to **114 surahs / 6,214 ayahs**, zero zero-glyph ayahs,
**zero unnumbered markers**, and per-surah counts matching the shipped data exactly.

These two need `bootstrap=True`, like Ishaq/Idris: `is_surah_start` renders through
`glyphmap.json`, which does not know these volumes, so the basmalah detector sees 2 blocks.

### `_digit_val` has an off-by-one that must NOT be fixed on its own

HQPB2 gids 169-178 are the ten digits; the range in `_digit_val` runs to **179**, which is a
body letter (the ya of `شَيۡءٖ`) scoring as a spurious "10". Narrowing the range looks
obviously right and is not: `is_markerish` keys off the same function to hold a glyph OUT of
x-overlap clustering, so gid 179 has been learned as the standalone key `HQPB2#179|©` in
every detmap. Narrow it and it starts joining clusters under keys nothing has ever seen, and
shubah falls **90.56% to 75.84%** on 1,286 UNMAPPED. Reverted, with the reasoning in the
docstring. It is harmless where it stands (a digit is only consumed within three characters
of a rosette, which measured zero times in these volumes), and fixing it means relearning.

### Silat meem al-jam': 5,786 bare meems per volume

The defining Abu Jafar feature. The plural meem is read as a full waw, `لَهُمُۥ`, and the
print draws it RED, which its own page legend calls **صلة ميم الجمع**. It is ONE composite
glyph carrying both the damma above the meem and the waw below (outline bounds -1035..1462,
ink on both sides of the baseline), and it comes in four advance widths for line fitting:
`Hamd2#54` (5,786), `#60` (303), `#53` (156), `#52` (2, and it is the one al-Fatihah uses).

The meem carries no other vowel - `عَلَيۡهِم` extracts as ع َ ل َ ي ۡ ه ِ م and then this
glyph, nothing else - so the same rule as the ishmam dot applies: it has to come out as the
vowel it replaced, or the word ships unvocalised. Which is exactly the shipped defect.

Three more letter glyphs were being dropped outright, each corroborated word for word
against the app's KFGQPC-verified Qaloon text, the other Madani riwayah:

| glyph | 271 / 40 / 21 per volume | shipped | now |
|---|---|---|---|
| `HQPB2#91` | the لأ of `ٱلۡأٓخِرَةِ` | `وَبِآخِرَةِ` | `وَبِالۡأٓخِرَةِ` |
| `HQPB2#159` | U+06E7 of `ٱلنَّبِيِّۧنَ` | kept in 1 word of 14 | all 24 |
| `Hamd2#76` | the tasheel `ءَٰا۬` | `عَلَيۡهِم نذَرۡتَهُم` | `عَلَيۡهِمُۥ ءَٰانذَرۡتَهُمُۥ` |

All 13 distinct words carrying `Hamd2#76` appear in Qaloon's own list of `ءَٰا۬`-initial
words, so the five-character emission is the source's, not an invention.

### `manualmap.json` needed family scoping

Gid numbering is stable across volumes; MEANING is not. `HQPB2#91` is the لأ ligature in the
Madani volumes and something else in the Kufi ones, and writing the Madani reading globally
cost shubah 1.7 points across three keys. A manual entry may now be prefixed `<fam>:` to
scope it, `fixdrops.py` writes scoped keys, and the 139 older unscoped entries still apply
everywhere.

### The wasl repair could never match a word that ended in a waqf sign

`apply_family_conventions` restores the naql vowel and dot on the article alef from the
family's verified bridge text. `_family_tables` strips pause marks from both sides of every
entry it learns, but the lookup passed the word **with** its waqf sign, so any such word
missed the table and went unrepaired: `اِ۬لۡعَٰلَمِينَۖ` came out `الۡعَٰلَمِينَۖ` while the
identical word one ayah later repaired fine because nothing followed it. **950 of Ibn
Wardan's 6,214 ayahs.** This bug is family-generic and will have been costing Yaqub and
Khalaf al-Ashir the same way.

A second fallback keyed on the **hamza-normalised skeleton** was added underneath it. Abu
Jafar reads the ibdal forms, so his `الۡمُومِنِينَ` never matches Qaloon's
`اَ۬لۡمُؤۡمِنِينَ` on the exact string and went unrepaired 59 times over; on the skeleton it
matches, and the vowel comes from the verified text rather than from a guess. (For the
record: the vowel is only 93% predictable from the preceding word's last character alone,
which is why the skeleton match is worth having and a blind rule is not.)

Naql marks: 9,755 shipped to **9,891**, with 45 words still short.

## 3g. Yaqub: an incomplete ladder that had been eating kasras all along

Ruways and Rawh needed no structural work at all. Both segment straight to 114 surahs at
**6204 and 6206**, their canonical Basri counts, with `bootstrap=True` and nothing else -
the two fixes banked from the Abu Jafar pass (`MSH_BANNER_RATIO` and the waqf-sign bug in
the wasl repair) were exactly what they needed, and both applied without a line of change.
The work was all in the glyph layer, and most of what it found was family-generic.

### The volumes' own legend decodes the coloured glyphs

Every Yaqub page carries it: **magenta = الحرف المخالف لحفص، red = الإمالة، blue = الإدغام**.
Reading the COLOUR of an unresolved glyph out of the PDF text layer (`sp["color"]`) sorts
the drop list before any guessing starts, and it is much faster than reasoning from
emission statistics. Two classes fell out immediately, both **Ruways only**:

| glyph | colour | what it is | count |
|---|---|---|---|
| `Hamd2#44` / `#45` | MAGENTA | ص carrying a small س: the notation for reading الصراط as السراط | 39 + 6 = **45** |
| `Hamdy2#207/204/149/201` | RED | a FILLED dot below the baseline: imalah kubra on the kaf of كافرين | **89** |

39 + 6 is exactly the Quran's count of صراط, and `#45` occurs only after the article, so it
carries the assimilation shadda and `#44` does not. The app's verified QiraahQunbul, the
other riwayah reading sin here, spells it `صِۜرَٰطٖ` with U+06DC SMALL HIGH SEEN, so that
is what these emit. **Rawh's volume contains neither glyph** - he reads a plain sad and has
no imalah in كافرين - which is the documented split between Yaqub's two rawis and the best
corroboration available that both readings are right. Neither glyph appears anywhere in the
Basri bridge volumes, so no amount of learning could ever have reached them: they are
`fixdrops.REAL` entries, scoped `basri:`.

### The kasra ladder was six entries short, and it cost every family

This is the big one, and it was NOT a Yaqub problem. `ZONEFLIP` performs a paired swap:
the shadda ladder `HQPB4#65..82` (one outline at fifteen stack heights, drawn ABOVE the
baseline) and its partner kasra ladder `HQPB4#165..176` (one outline at twelve heights,
BELOW it). §3b got the swap right but listed only 165/169/170/173/174/176 on the kasra
side, leaving **166/167/168/171/172/175 free for the context pass to mislearn** - which it
did, giving `#166` twenty-seven shadda rules and `#175` twenty-nine.

The failure mode is silent and expensive. When such a glyph renders a shadda beside its
partner, which ZONEFLIP correctly pins to a shadda, `collapse_doubled_marks` folds the two
into one and **the kasra is simply gone**: `رَبِّ` shipped as `رَبّ`. That is 1,076 words in
Ruways alone and 312 diffs in the duriabiamr round-trip. Completing the ladder is worth

| | before | after |
|---|---|---|
| shubah (THE acceptance metric) | 90.56% | **90.59%** |
| duriabiamr ayah-exact | 55.28% | **62.16%** |
| susi ayah-exact | 43.07% | **48.15%** |
| duriabiamr word accuracy | 94.03% | **95.13%** |
| susi word accuracy | 91.24% | **92.34%** |

Gids 66, 72 and 78 are absent from every volume, so the shadda ladder's own gaps are real.

### ZONEFLIP can now hold a POSITIONAL rule, because one glyph has two jobs

`HQPB5#128` is a shadda-with-fatha outline that the map had learned as a bare alef off a
four-occurrence sample. It appears **850 times per Yaqub volume against 4 in the whole of
duriabiamr and 0 in shubah**, so the bridges have nothing to teach from and the geometry has
to decide. Adjudicating all 1,620 occurrences across both volumes against the verified Duri
text splits them perfectly, with no context seeing both answers:

* **word-final -> the alef of `لَا` / `إِلَّا`** (1,475)
* **anywhere else -> the shadda + fatha of `فَضَّلۡتُكُمۡ` / `اَ۬لضَّآلِّينَ` / `وَاَلرُّكَّعِ`** (145)

A flat ZONEFLIP value cannot express that, so a value may now be a small dict keyed `"$"`
(word-final) and `"*"`. Two traps in defining "word-final", both of which bit:

1. **`render_det` is handed a WHOLE AYAH**, in which words are separated by `sp| ` tokens.
   Testing only `i + 1 >= len(keys)` marks just the last word of the ayah and silently takes
   the interior branch for every other one. `وَلَٰكِن لَّا` came out `وَلَٰكِن لَّ`, 748 words
   per Madani volume - caught only because the Abu Jafar candidates were re-emitted and
   diffed. Test for a following space too.
2. **A letter that already carries its shadda cannot take a second one**, so an interior
   occurrence there is the alef after all: `تَوَلَّاهُ` (22:4), where the lam's shadda comes
   from its own glyph.

### `collect_pairs` assumed equal ayah COUNTS meant equal ayah BOUNDARIES

They do not, and the learner had no way to notice. Surah 3 of the Basri volumes has 200
ayahs and so does the app's Duri text, but they split ayah 48 differently, so every pair
from there on handed the learner one volume's glyphs beside a DIFFERENT ayah's text.
Measured with each family's own detmap doing the rendering:

* **shubah: 6,122 of 6,122 pairs correspond.** The Kufi training data is clean, which is
  most of why Kufi is the strong family.
* **duriabiamr: 329 of 3,374 pairs (9.8%) are paired with the wrong ayah**, at skeleton
  similarity 0.33-0.63 against >=0.90 for real pairs. Nothing sits between, so
  `extract.PAIR_CUTOFF = 0.75` discards drift without touching a genuine pair - including
  the badly-rendered ones, which are exactly the signal we must not lose.

`collect_pairs` now takes a `render=` callback and rejects non-corresponding pairs, and
**`ctxpass` calls it instead of carrying its own copy of the same wrong assumption** - two
copies of one bug was the real defect. Pass `render=` whenever a detmap already exists.

### The Basri bridge texts are numbered 6217, and the PDFs are 6204

Worth knowing before trusting any Basri round-trip number. The shipped QiraahDuri and
QiraahSusi carry **6217** ayahs, which is not a canonical count for any reading, while the
Islamweb Basri volumes are 6204. They differ in **40 of 114 surahs**, all of which
`collect_pairs` skips outright. Shubah matches its text exactly (6236 = 6236), and that
difference alone explains most of the gap between the families' scores. The honest Basri
figures, with drifted pairs excluded, are in the table above; the raw `final.py roundtrip`
numbers are lower because it still scores those pairs.

Adjudicated word by word against the verified QiraahDuri - where a word appears there with

| | Ruways | Rawh |
|---|---|---|
| candidate matches Duri, shipped does not | **1,916** | **1,834** |

**All ten candidates were re-emitted** from the corrected map, since the ladder fix is

## 3h. Madani: three numbers that were measuring the wrong thing, and one rule worth 900 words a volume

Madani looked like the weakest family by far (17.85% and 14.73% ayah-exact against Kufi's
90.59%). Most of that gap was the measurement, not the extraction, and separating the two
was the whole of this pass. What was left underneath is real, and it is fixed by rules
rather than by glyphs.

### The metric was scoring 84% of one volume and comparing renders to the wrong ayah

`collect_pairs` and `roundtrip` both required a surah's ayah COUNT to match before pairing
anything in it, then zipped positionally. On the Qaloon volume that dropped 15 surahs and
970 ayahs (15.6%) outright, and on the Basri volumes 40 and 41 surahs. The counts are not
the disagreement, though: the marker sequences in every one of those Qaloon surahs run
1..N unbroken, so the print really does number al-Zalzalah at 8 while the app's Qaloon
splits `يَوۡمَئِذٖ يَصۡدُرُ اُ۬لنَّاسُ أَشۡتَاتٗا` from `لِّيُرَوۡاْ أَعۡمَٰلَهُمۡ` and gets 9.
Seven of those nine ayahs correspond exactly and were being thrown away with the other two.

`extract._ayah_alignment` aligns the two ayah lists instead (banded Needleman-Wunsch over
skeleton similarity, gaps cheap because a gap is what a merge or a split looks like from
here, sub-0.6 matches scored worse than any number of gaps). Ayah 1 is re-attached rather
than aligned: it always corresponds, and its glyphs carry the surah header and the
basmalah, so it scores far too low to survive. The pairing is unchanged where nothing is
wrong - Kufi is 6,122 pairs before and after - and recovers what was being dropped
elsewhere:

| family | pairs before | after |
|---|---|---|
| kufi | 6,122 | 6,122 |
| madani | 11,157 | **12,150** |
| basri | 6,098 | **12,015** |

`roundtrip` prints a coverage line now, because the number used to mean the accuracy over
the whole volume for shubah and the accuracy over 74 of 114 surahs for duriabiamr.

### The app's Madani and Basri texts flatten every waqf sign, and it was 7,218 diffs

QiraahQaloon and QiraahWarsh carry 9,757 and 9,820 U+06D6 and not one other pause sign;
their volumes print the ordinary four-way system (3,327 U+06D6, 1,915 U+06DA, 585 U+06D7),
and the app's Madani and Basri texts also carry ~430 rub rosettes against the volumes' 198.
That is an edition difference, not an accuracy one, and left in the comparison no ayah
carrying any pause sign could ever match. All ten candidates already ship the volumes'
four-way marks, so `roundtrip` now prints a **pause-blind** figure beside the raw one and
classifies its diff histogram on the pause-stripped strings. The raw number is kept because
a regression in it would still be real.

### U+06EA does two jobs and was being deleted for one of them

`apply_family_conventions` dropped every U+06EA before re-learning the wasl signs from the
bridge. Under a wasl alef that is right; anywhere else U+06EA is the **taqlil** dot, and
Warsh's text carries 2,569 of them with only ~664 on a wasl alef. So ~1,900 real marks per
volume were being deleted, which read as "the print does not draw taqlil" - and that in
turn is why the dot was being emitted as U+065C in the first place. Both halves are fixed:
the strip is now positional, and `imalah_mark(family)` returns U+06EA for Madani (Warsh and
Abu Jafar read taqlil, and the app's own Madani texts carry 3,264 U+06EA against a single
U+065C) while Kufi keeps U+065C (Hamzah and al-Kisai read imalah kubra). Basri writes both
and stays on the Kufi default with the bridge repairing the taqlil words. Worth +8.2 points
on warsh and +3.9 on duriabiamr.

### The wasl vowel is not a lookup, it is the join being written out

This is the pass's real find, and it is worth more than everything above.

The vowel written on a wasl alef (`اُ۬للَّهُ` / `اِ۬للَّهِ` / `اَ۬للَّهَ`) is whatever sound
the previous word ends on. It is not a property of the word at all, so a table keyed by the
word cannot get it right: `ٱللَّه` occurs 2,699 times with all three vowels and the
`("*", word)` fallback handed every one of them the commonest.

`final.carried_vowel` derives it instead: walk back through the previous word's sounds,
taking a short vowel as itself, a tanween as a kasra, a dagger alef as a fatha, a silent
alef as whatever precedes it (`قَالُواْ` ends on the waw's damma, `خَيۡرًا` on its tanween),
and an imalah'd final ya as a fatha rather than a kasra. Audited against every occurrence in
the three verified app texts that use the notation:

| | rule agrees |
|---|---|
| QiraahQaloon | 10,541 / 10,546 (99.95%) |
| QiraahWarsh | 10,537 / 10,548 (99.90%) |
| QiraahDuri | 10,543 / 10,543 (**100.00%**) |

The residue is the muqatta'at of 3:1 and five U+06DF imperatives, not a rival rule.

Turned on the candidates it had never seen, the same audit is a direct quality measure:

| | wasl vowels contradicting the rule |
|---|---|
| verified QiraahQaloon | 5 of 10,531 (0.05%) |
| standing ibnwardan candidate | **894 of 10,268 (8.71%)** |
| standing ibnjammaz candidate | 903 of 10,323 (8.75%) |
| standing ruways candidate | **1,287 of 10,248 (12.56%)** |
| standing rawh candidate | 1,281 of 10,245 (12.50%) |
| new ibnwardan emit | **1 of 10,272 (0.01%)** |

The six Kufi and Shami candidates have no wasl notation at all (0 of 0), so this is a
Madani and Basri fix only, and `khalaf` re-emits byte-identical.

### The sign is lexical, and the page says where one belongs

Which of U+06EC / U+06EA / U+06DF a word takes IS a property of the word: across 10,774
occurrences in Qaloon only `اتبعوا` ever takes two (11 to 1). So the sign comes from a
skeleton-keyed table and the vowel from context, and each question is answered by the thing
that knows it. Three separate bugs sat in that table:

- it only learned words spelled `alef, vowel, U+06EC/U+06EA`, so the ~120 `اُ۟عۡبُدُواْ`
  imperatives were never learned at all and every one of them shipped bare. Widening the
  condition to include U+06DF is worth +1.6 points on qaloon, +1.3 on duriabiamr and 130 of
  the 142 adjudicated wins below;
- the homograph guard counted only bare-alef words, so `أَلِيمٞ` - which folds to a wasl
  word's skeleton - looked unambiguous and took a sign it never has, 64 words per Warsh
  volume;
- a word whose skeleton IS shared (`إِذۡ`/`ا۪ذۡ`, `أَوۡ`/`اَ۬وۡ` are both spellings of the
  same word in the same text) can still be settled, because `CL|HQPB5#7|$` is the glyph the
  print draws the sign with. It used to emit nothing; it now carries a marker through, and
  a marked word may take the majority sign without passing the homograph guard.

### A catch-all rule built from one observation

`ctxpass` gave a key a context-free `*` emission on purity alone, with no floor. One stray
alignment was therefore 100% pure and won: `CL|HQPB4#52|R` is one rung of the iqlab ladder
(HQPB4 41-52, a single fatha-plus-small-meem outline at ten stack heights, and gids 40, 42
and 51 are genuinely blank), the map reads it `َۢ` on 110 occurrences, and six observations
of `اَ` gave it a `*` that shipped `تَوَّاباَا` for `تَوَّابَۢا` in every volume of the family.

`*` now needs 3 observations, and needs at least as many as the detmap's own majority when
it CONTRADICTS the detmap. Pinning the whole ladder in ZONEFLIP instead was tried first and
measures worse everywhere (shubah 97.84 -> 97.70), so the alef is real in some positions:
this is a case for evidence, not for geometry.

### The iqlab tanween is ordered differently by family

Tanween with iqlab on a final alef is written `ـاَۢ` in the Madani texts and `ـَۢا` in the
Kufi and Basri ones. 87 words in Qaloon and 72 in Warsh take the first order and NOT ONE
takes the second; Duri and Shubah are the exact mirror, 87 and 87 the other way. Same word,
same sound, and the print draws the same glyph either way, so no amount of glyph work can
decide it. `apply_family_conventions` rewrites it for Madani, looking past a trailing waqf
sign.

## 3i. Khalaf al-Ashir: the same glyphs behind different character codes

The last pair, and almost none of the work was in the glyph layer. Both volumes segment
straight to **114 surahs / 6,236 ayahs** with `bootstrap=True` and per-surah counts
canonical, and their glyph streams are byte-identical to each other (605,227 tokens,
75,858 spaces), so everything below was found once and emitted twice.

### 1,613 words were losing a glyph, and only five of them were new glyphs

A detmap key is `font#gid|char`, where the char is the volume's own cmap code. A volume
embeds its own font SUBSET, and these two re-code nearly everything: `HQPB2#179` is the ya
that Shubah codes `©` and they code `\uf6d9`. Nothing learned matched, so **1,294 ya
letters fell out** of `شَيۡءٖ`, `ٱلَّتِي`, `مُوسَىٰ` and `يَٰبَنِيٓ`, and sixteen more gids
went the same way.

Every one of the sixteen was already known. Each was confirmed three ways that agree
completely: the rendered outline, the Hafs word it sits in, and the emission the Kufi map
had already learned for the SAME gid under a different code.

| gid | is | gid | is |
|---|---|---|---|
| `HQPB2#179` | ي (1,294) | `HQPB2#212` | ئ |
| `HQPB1#218` | ف | `HQPB2#214` | ن |
| `HQPB1#215` | غ | `HQPB2#215` | ث |
| `HQPB1#111` | ر | `HQPB2#216` | ت |
| `HQPB1#97` | خ | `HQPB4#111/#112/#126` | shadda + damma |
| `HQPB1#125` | س | `Hamd2#170/#172` | imalah dot |
| `HQPB2#125` | ئ | `Hamd2#198/199/200` | decorative basmalah |
| `HQPB2#112` | ي | | |

So the fix is not sixteen manual entries, it is **`final.GIDFALLBACK`**: where a family's
learned keys for one gid signature all agree, that emission belongs to the GLYPH rather
than to the code it arrived under, and an unseen code for it takes the same answer.
Unanimity is the whole guard, and it is scoped per family for the reason §3f gives.
Signatures strip the char from every member of a cluster, so `CL|HQPB1#123|>||HQPB5#20|1`
matches too. **1,613 words with a dropped glyph fell to 13.** It costs shubah nothing
(90.61% before and after), because shubah's own keys hit exactly.

### `mshmap.py` was matching `MSH` case-sensitively

These volumes name the farsh font `MshQuraan1`; every other volume calls it `MSH-Quraan1`.
`extract.DROP_PREFIX` and `_is_msh_text` already accept both spellings and `mshmap.py` did
not, so it mapped **nothing** for this family and read as "no farsh layer here" rather than
as a miss. The cmap codes turn out to be identical between the two spellings (`γ`, `υ`,
`∼`, `∫`, `ÿ`), and every gid means what §3c, §3d and §3e already recorded, corroborated on
the same evidence words: `#210` the standalone ء of `جَبۡرَءِيلَ`, `#96` the ya of
`وَلِيَسۡتَبِينَ`, `#97/#98` the لا of `تَوَلَّاهُ`, `#49` the U+06E0 of `يَتَسَنَّهۡ`,
`#8` the قلى of `ٱلۡأٓخِرَةِۗ` at 3:148. Not one new decision, 39 keys written.

### A font is embedded SIX times over, and only the first subset was ever read

`glyphsheet.py` and `zoneaudit.py` both resolved a font to its FIRST xref. These volumes
embed six subsets of each font, one per page range, and a subset carries an outline only
for the gids its own pages draw. Read that way `HQPB2#215`, `HQPB2#216`, `Hamd2#170` and
`Hamd2#172` all came back with no outline at all, which is indistinguishable from the
genuine spacers of `fixdrops.SPACER_GIDS` and would have retired four real glyphs as page
furniture. Both tools now keep every subset and take the first that has ink. **An empty
cell in a contact sheet is only evidence of a spacer once every subset has been asked.**

### The five that were genuinely new

`Hamdy4`, a font no other volume in the series uses: `#172` the imalah dot on `جَآءَكُم`
(2:92) and `فَجَآءَهَا` (7:4), and `#106/#107/#10` the ل, the ا and the hamza of
`لَّأَذَقۡنَٰكَ` (17:75). The hamza is emitted as the COMBINING hamza so `compose_hamza`

cannot reach that, so `fixdrops.REAL_KEYS` now exists for whole-cluster decisions.

that reach zero.

## 3j. Four fixes that came out of this pass and belong to every family

Each was accepted on the acceptance metric and none of them is about Khalaf al-Ashir.

### A waqf sign was landing inside the word

The farsh layer redraws a whole differing word, its waqf sign included, and the redraw is
clustered by x-overlap with the letters rather than trailed after them. So the sign arrived
before the word's last letter: `بِهِمَۚا` for `بِهِمَاۚ` (2:158), `أَجۡرًۖا` for `أَجۡرًاۖ`
(6:90). Where the black body layer prints the same sign as well the two then sit apart,
`collapse_doubled_marks` cannot see them as a pair, and the word ships `ۚۚ`.

A waqf sign never sits inside a word, so `final.pause_to_word_end` moves a stray one to the
end - before the collapse, so the duplicate becomes adjacent and folds. **Worth +0.19 on
shubah on its own**, so it was never a Khalaf al-Ashir problem.

### Word-final ya: `ي` or `ى`, and the print draws one glyph for both

`HQPB2#179` is the same outline in `شَيۡءٖ` and in `مُوسَىٰ`, so restoring it as the ya put
`مُوسَي` into 56 words a volume. The orthography decides it exactly:

    carries a sukoon          -> `ي`   the -ay diphthong, `ٱثۡنَيۡ` `يَدَيۡ`
    else preceded by a kasra  -> `ي`   `فِي` `ٱلَّتِي` `أَخِي`
    else                      -> `ى`   `عَلَىٰ` `إِلَى` `هُدٗى` `رَمٜىٰ`

**5,422 of 5,422 in the verified Hafs, 5,452 of 5,452 in Shubah, 5,294 of 5,294 in
Qaloon.** One clause of it is an edition convention rather than orthography, and the Basri
texts take the other side: where an imalah or taqlil dot precedes, QiraahDuri and
QiraahSusi write the ya (`مُوس۪يٰ`, `وَاَلنَّصَٰرٜيٰ`, 605 words, and it is 605 of the 605
that disagree) while Shubah writes `رَمٜىٰ`. Applied blind that clause alone cost susi 2.4
points, so `maqsura_rule` takes the family.

### `zonectx.py --write` was overwriting other families' work

It runs for one family, sees only that family's ctx map, and wrote the whole file. The six
kasra rungs of §3g are contradicted in the BASRI map and nowhere else, so a later kufi-only
run dropped them silently - and an incomplete kasra ladder deletes kasras, which is the
1,076-word failure that pass existed to fix. It **merges** now, and it takes
`QIRAAT_FAMILY`; run it for every family:

```bash
for f in kufi madani basri; do QIRAAT_FAMILY=$f python3 zonectx.py --write; done
```

`HQPB5#128`'s positional entry could not be regenerated at all, so it lives in
`zonectx.POSITIONAL` now rather than only in the JSON.

### Three separate ways the zone pass was overreaching

1. **It cannot judge a glyph whose ink SPANS the baseline**, and that is exactly the rungs
   drawn nearest the line. `HQPB4#158` is one, ink -181..166, and it emitted a shadda in
   every family while its own ladder emitted the kasra - which cost the kasra of
   `يُؤَخِّرُهُمۡ` and seven more words a Kufi volume, the §3g failure one rung further on.
   A **ladder-identity pass** now clusters gids by bounding box with a small tolerance (a
   ladder is one mark at many stack heights, so its members share a box) and lets the
   group's zone-decided majority name the rungs geometry could not. On HQPB4 that recovers
   exactly the ladders the earlier passes found by hand: 402x397 the bare shadda, 510x347
   the kasra, 493x971 shadda+damma, 681x722 shadda+fatha, 508x631 the plain damma. It
   fires on three keys and only ever overrides a "spans" member. Exact path identity was
   tried first and is too strict: the font carries four bezier variants of the kasra stroke.

2. **"Ink above means the bare shadda" was verified for fifteen glyphs and applied to all.**
   §3b eyeballed the fifteen HQPB4 rungs and was right about them; running this for madani
   and basri turned up ink-above rows that are nothing like a shadda. `HQPB5#48` is
   1692x823 against the shadda's 402x397 and its own other key emits a maddah; `HQPB5#69`
   emits an alef. Forcing those to a shadda cost **133 Madani words**, `بِالۡإِثۡمِ`
   shipping as `بِالۡإّثۡمِ`. The shortcut now has to earn itself by matching the size of
   the verified bare shadda; anything else takes the ordinary treatment or is left alone.

3. **A ZONEFLIP entry is a flat override, so pinning a key threw away its CORRECT context
   rules.** `HQPB4#35` is a kasratain drawn together with the small saad-lam-alef pause
   sign, and its ctx knows to emit `ٍۖ` word-finally and `ٍ` before a space; pinning the
   bare `ٍ` deleted that sign from 33 words a Madani volume. `render_det` treats ZONEFLIP
   as a FILTER now: a ctx rule already on the right side of the baseline is knowledge this
   pass does not have and is left alone, and only a rule on the wrong side is replaced.
   `zonectx.mark_zone` was also refusing to judge any emission carrying a non-vowel, which
   is why `ٍۖ` counted neither for nor against its key; it judges on the vowels alone now.

## 4. Imalah: RESOLVED, and it went through two wrong answers first

Both volumes mark Hamzah's imalah in full. Getting there needed three corrections, and the
wrong turns are worth knowing because the same trap will recur on the other riwayat.

1. Khallad emitted 152 marks against Khalaf's 1,348, so it looked like a volume that does
   not mark imalah. **Wrong.** Khallad draws the dot in the `Hamd2` font (gids

   discarded ~1,737 of them. `hamd_imalah.py` recovers those.
2. That left Khallad at 1,878 and Khalaf at 1,348, i.e. 523 words Khallad marked and Khalaf
   did not, which looked like Khallad over-marking. **Also wrong.** Every one of the 523 is
   a textbook imalah word (`ٱلنَّصَٰرىٰ`, `بُشۡرىٰ`, `أُنثىٰ`, `ٱلدُّنۡيا`, `جآءَ`), so it was
   *Khalaf* that was short.

   `ٱلنَّصَٰرىٰ`. Khalaf draws it in `MSH-Quraan1` gid 38, and `page_tokens` was dropping
   that whole layer as page furniture (`MSH` is in `DROP_PREFIX`). 2,846 dots in Khalaf
   against 24 in Khallad, all discarded.

`extract._is_imalah_dot()` now recognises both spellings (`HQPB5#20` and `MSH-Quraan1#38`)
and routes them through the existing geometric dot-attachment, which normalises them to one
token, so `render_det` needed no change.

## 5. The idgham-shadda asymmetry is genuine

khalaf carries ~3,400 idgham shaddas (a shadda on the following word's first letter after
tanween/noon-sakin, e.g. `غِشَٰوَةٞۖ وَّلَهُمۡ`) and khallad carries none. Fresh extraction of both
volumes with identical machinery reproduces it (khalaf 26,249 shaddas, khallad 22,632), so
it is a **property of the two printed volumes**, not an extraction artefact.

Unlike the imalah case this one held up, because it is not about a missing glyph mapping.
**Do not normalise it in either direction** without a qari's ruling. Note the app's other
19 riwayat follow the KFGQPC convention (no such shadda), so khalaf will look different in
comparison mode. That is faithful to its source.

### Ishaq / Idris are identical IN THE SOURCE, not because of a bug

Previously logged as a pipeline defect. It is not one. Both volumes were re-downloaded and
re-extracted from their own PDFs:

* the two PDFs are genuinely different files (md5 `b648f9b5…` vs `81dcf3b0…`, 8,137,508 vs
  8,198,511 bytes);
* their extracted glyph streams are **byte-identical** (700,987 tokens, same hash);
* rendering the same page from each shows identical Quranic text, differing only in the
  header: `برواية إسحاق عن خلف العاشر` vs `برواية إدريس عن خلف العاشر`.

**Islamweb published one body text under both rawi names.** Our identical
`QiraahIshaq`/`QiraahIdris` are therefore faithful to the source, and fabricating
differences would be wrong.

**RESOLVED 2026-08-25, and the answer is that islamweb is right.** Via al-Durrah
al-Mutammimah, which is the path a mushaf of the three completing readings prints, nothing
is transmitted differently between Ishaq and Idris at all. Three independent lines agree:

* **The dedicated book says so.** `موئل الشاكر بقراءة خلف العاشر براوييه إسحاق وإدريس وأوجه
  الخلاف بينهما من طريق الدرة المتممة للقراءات العشر`, by حامد شاكر الشقاقي العاني, 201pp,
  foreword by د. نجم عبد الله مطر الدليمي of the mushaf printing committee in Iraq, finished
  26 Shawwal 1441 (June 2020). Free PDF:
  `https://www.alukah.net/Books/Files/Book_12136/BookFile/muayil_alshaakir.pdf`. The author
  colour-coded the whole Quran to separate the qari's readings from the rawis' and concludes
  in his khatimah (p. 180): `وفيما يبدو أنه لم يظهر أي خلاف بين الراويين من طريق الدرة`
  `المتممة، لهذا اخترنا اللون الأخضر للقارئ فقط` - no difference between the two rawis
  emerged, so green marks the qari alone. He repeats it in the same list of contributions.
  A qiraat reference puts the usul side identically: `يتفق الراويان (إسحاق وإدريس) في جميع الأصول`.
* **Islamweb's own series says so.** They separate rawis wherever the transmission does. Our
  candidates differ pair by pair: Khalaf/Khallad 2,523 ayahs, Hisham/Ibn Dhakwan 603,
  Ruways/Rawh 524, Abu Harith/Duri al-Kisai 437, Ibn Wardan/Ibn Jammaz **58**. Khalaf
  al-Ashir is 0 of 6,236, and a publisher who bothered to differentiate a 58-ayah pair did
  not get lazy on this one.
* **Their audio says so.** The app ships a reciter feed per rawi (`eshaq_khalaf`,
  `edris_khalaf`, both Muftah Alsaltany). Every surah is exactly 25 bytes apart, which is the
  length difference between the two rawi names in the ID3 title; al-Ikhlas decodes to an
  identical audio payload from both feeds. One recording, retagged, al-Baqarah included.

Where the two DO diverge is Tayyibat al-Nashr, the greater ten, in which Ibn al-Jazari gives
Idris two turuq (the `سكت إدريس` question among them). That is a different path and largely a
performance-level khilaf, not something a Durrah mushaf writes.

Caveat on the inference: islamweb's volumes carry NO front matter (page 1 is already
al-Fatihah), so they never state their path. Al-Durrah is inferred from their text matching
exactly where al-Durrah has no difference while all four other pairs differ.

Also checked: there is no independent source to switch to even if we wanted one. Every free
"Ishaq mushaf" and "Idris mushaf" on quranpedia and archive.org is republished islamweb
(quranpedia credits `الشبكة الإسلامية`).

**So the data is correct and stays untouched. What was wrong was the presentation**, and that
is now fixed in the app (2026-08-25): `QiraatProfiles.sharedTextRiwayat` plus
`shareOneText`/`sharedTextPartner`/`shortName` and the two strings
`sharedTextExplanation`/`sharedTextShortNote` carry the fact, and four surfaces show it - each
narrator's profile page gets a "THE SAME TEXT AS <other>" section, both gain a hallmark line,
Khalaf al-Ashir's "ITS TWO RIWAYAT" list gains a footer, the comparison sheet's Head-to-Head
footer swaps the generic "identical wording" line for the explanation whenever the pair is

identical text in the data.

### The method that worked

1. **Baseline first.** `final.py roundtrip <bridge>` before touching anything. Never accept
   a change that lowers it. Every claim below was accepted or rejected on this number.
2. **`zoneaudit.py` AND `zonectx.py`** - geometry finds mismapped marks with no guessing
   (kasra below the baseline, shadda above; anything crossing that line is wrong). Run both:
   `render_det` reads the context map first, so a glyph can pass the detmap audit and still
   render wrong. That is exactly where the shadda ladder hid for a whole session.
2b. **When a fix measures WORSE, suspect a paired glyph rather than a wrong identification.**
   Forcing the ladder to shadda scored 55.55% against 88.91%, which read as "these are not
   shaddas". They are; its partner glyph was carrying the shadda and had to move back at the
   same time. A half-applied swap is worse than no swap. Before abandoning a fix the geometry
   supports, look at what sits NEXT to the glyph in the stream.
2c. **Check the coloured layers before believing a letter is absent.** The volumes print
   their farsh in a separate font and leave a zero-width spacer in the body layer, so a
   missing letter leaves no gap and no unresolved-glyph warning. See §3c; the page legend
   tells you what each colour means.
3. **`showdrops.py`** - see what `emit` is actually losing. Do not trust the raw
   "unresolved" count: 95% of Hamzah's was decorative page furniture, and the handful of
   real losses underneath it was invisible until they were separated. `fixdrops.py` does
   the separating.
4. **`glyphsheet.py`** on any suspect glyph. Reading the outline beats reasoning about
   emission statistics, which are confidently wrong surprisingly often.
5. **`findpage.py`** when two sources disagree and you need a ruling. Rendering the printed
   page has now settled every open question it has been pointed at: the imalah dot,
   Ishaq/Idris, `جَبۡرَءِيلَ`, `وَلِيَسۡتَبِينَ`, `وَلَٰكِنِ ٱللَّهُ` and `ذُنُوبِهُمُ`. It also
   carries the colour legend. Use it earlier than feels necessary.
6. **Cross-compare the two rawis**, then against Hafs and Shubah. Where the two rawis of one
   qari disagree, at least one is corrupt: highest-yield list. Where they agree but differ
   from Hafs, it is probably genuine farsh. Where one rawi has a mark and the other does
   not, check the *words* are the right linguistic environment before believing either.
7. Re-run the round-trip. Keep only what does not regress it.
8. **Check what the METRIC is measuring before optimising the extractor.** Madani spent a
   session looking like the weakest family on a number that was scoring 84% of one volume,
   comparing some renders against the wrong ayah, and counting a waqf layer on which the
   app's own text is a different edition from its own volume. None of the three was visible
   from the number itself; all three showed up the moment the pairing and the diff histogram
   were made to say what they had covered. A metric that cannot say what it skipped is
   telling you about itself, not about the data.
9. **A rule that reproduces a verified text is a quality measure you can turn on a
   candidate.** `carried_vowel` was written to fix a defect, but the useful thing about
   auditing it at 10,543/10,543 on QiraahDuri first is that its violation COUNT then reads
   as an error count anywhere else: 5 in the verified Qaloon, 894 in the standing ibnwardan
   candidate, 1,287 in ruways. That is a far sharper instrument than a skeleton-pool
   adjudicator, which abstains on exactly the cases a contextual rule decides (873 of
   ibnwardan's 1,120 changes came back "both attested").
10. **A catch-all learned from a handful of observations can override a well-supported map.**
   `ctxpass` gated its `*` rule on purity alone, so one stray alignment scored 100% and won.
   Purity without support is not evidence, and a rule that CONTRADICTS the deterministic map
   is making the stronger claim, so it needs the stronger case.
